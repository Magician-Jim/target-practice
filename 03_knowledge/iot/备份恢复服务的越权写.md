# 备份恢复服务的越权写

## 一句话

当普通用户能够驱动一个以 root 运行的“恢复”服务，并且目标包含 cron、SSH 或启动配置时，
备份功能就会变成合法外壳下的 root 持久化接口。

## 图解

```text
低权限 Web 用户
  │ 写入 job / staging
  ▼
root backup service
  │ 读取任务并复制文件
  ▼
/root/.ssh/authorized_keys
或 /etc/cron.d/*
```

## 怎么找

1. `ps -eo user,pid,args` 找 root 运行、接受 token 或本地 HTTP 请求的服务。
2. 查看 `jobs/`、`staging/`、配置目录和 systemd unit 的用户、组、mode。
3. 搜索 `restore`、`import`、`apply`、`backup`、`config` 等关键词。
4. 确认恢复目标是否包含控制面路径，而不只是业务数据目录。
5. 用正常业务请求验证，不要先做破坏性覆盖。

## 设计层面的判断

- allowlist 里有高危路径，不等于设计安全。
- token 写在 argv 中，可能被同机用户通过进程列表读取。
- `root:root` 再 `chmod 0600` 只保证文件安全，不保证“谁能创建任务”安全。
- 备份服务应按能力拆分，不能让一个恢复任务覆盖身份认证和启动链。

## 迁移到固件

重点检查：

- 配置导入/恢复、固件回滚、日志清理接口；
- 从 `/tmp/uploads` 到 `/etc/init.d`、`/etc/cron*`、SSH 密钥或 nvram 写入的路径；
- Web 用户与维护进程之间共享的可写目录；
- 服务命令行、固定 token 和未认证 localhost API。
