# 周报规范（打靶机版）

> 本文件继承实验室《项目周报填写要求》，并对靶机周报做最小适配。
> 母本：`..\..\Seed Intelligent Analysis\weekly_report\周报填写要求.md`
> 原则：**格式不变，内容替换**。导师看两份周报时不应该需要切换阅读习惯。

---

## 一、继承自实验室的四条硬约束

1. **四大结构，顺序固定**：
   - ① 遗留问题跟踪（每个问题必须有明确结论）
   - ② 本周进展（正常推进的内容）
   - ③ 下周计划
   - ④ 需要老师把关确认的问题（末尾汇总）
2. **总分结构**：每部分先写"总"（一句话），再写"分"（表格/条目）。导师时间有限时只看每部分的"总"。
3. **遗留问题必须闭环**：每条在"结论"列写清 ✅已解决 / 🔄有进展 / ⚠️无进展 / ❓待老师确认，**不能写"处理中"**。
4. **需要拍板的事用【待老师确认】标记**，并在第四部分统一汇总，方便导师按序号直接回复。

---

## 二、靶机周报的字段映射

| 实验室四段 | 靶机场景下填什么 |
|---|---|
| ① 遗留问题跟踪 | 上周没打穿的靶机、没搞懂的技术点、没确认的选题 |
| ② 项目整体进展 | 本周这台靶机的攻击链、关键根因、与 IoT 的映射 |
| ③ 下周计划 | 下台选题 + 要补的 1–2 个知识点 + 需要的环境/资料 |
| ④ 待老师确认 | 选题是否合适、方向是否要调整、要不要提前转固件 |

**靶机周报在②里比实验室周报多两节**：`关键根因`和`与 IoT 方向的映射`。这两节是你和"只会刷靶机的同学"的区别所在，必须写满。

---

## 三、硬性写作要求

| 要求 | 说明 |
|---|---|
| 结论前置 | 开头【总体摘要】2–3 句，读完知道这周干了什么、卡在哪 |
| 长度 | 正文 1–2 页。导师不会看 6 页流水账，但会认真看根因那节 |
| 禁止流水账 | 不写"我学会了 nmap"，写"这个服务的默认配置泄露了什么，同类问题在固件里怎么出现" |
| 卡住要如实写 | "没拿到 root + 卡点分析"的周报，质量高于硬凑的"我打完了"。导师一眼能看出真假 |
| 每份留 1 个具体问题 | 具体到技术点，不写"请老师指导"。这决定他下周一会不会认真回你 |
| 保留证据 | 关键截图进 `05_evidence/`，周报里引用文件名，不要贴满屏截图 |

## 四、命名与交付

- 文件名：`打靶机周报-MM.DD至MM.DD_黄子沣.md`
  （对齐实验室既有命名：`iotamoeba项目周报-10.12至10.18_黄子沣.md`）
- 存放：源文件在 `01_targets/<靶机>/REPORT.md`，导出副本到 `02_reports/`，两者内容一致。
- 交付：周一上午发 `.md`；导师若要 PDF，再用 `pandoc` 或 Word 导出同名 PDF。
- 周期口径：**周一至周日**，与实验室周报一致。

## 五、反面例子（自查用）

❌ **流水账型**：
> 本周我学习了 nmap 的使用，扫描了靶机，发现了 22 和 80 端口，然后用 hydra 爆破得到了密码，最后用 sudo 提权拿到了 root。

问题：没有根因、没有判断、没有可迁移结论。换成任何人打这台机器，这段文字都一样。

✅ **结论型**：
> 本周完成 THM Basic Pentesting（Easy），独立拿到 root，耗时 3.5 h。
> 关键根因：SMB 共享允许匿名枚举，泄露了用户名清单；配合 SSH 口令策略缺失，形成"用户名枚举 → 弱口令"的完整链路。
> 可迁移性：同类问题在 IoT 固件里表现为 `/etc/shadow` 弱 hash + telnet 默认开启，我在 `03_knowledge/iot/` 记了一条对应检查项。
> 卡点：提权阶段误判了 sudo 版本，浪费 40 分钟，教训是**先 `sudo -l` 再谈其他**。

## 六、四周自查

每 4 周回看一次自己的周报：

1. 第二部分的"总"能不能独立读懂？
2. 根因那一节，是"我用了什么"还是"为什么能成"？
3. 第四部分的问题，导师有没有回？没回说明问题不够具体，或者根本不需要他拍板。
4. 有没有一条结论进了 `03_knowledge/`？没有的话，这 4 周只是在重复劳动。
