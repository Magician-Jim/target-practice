# 周报规范（打靶机版）

> 本文件继承实验室《项目周报填写要求》，并结合老师对打靶机周报、靶机笔记和
> WP 的最新要求进行细化。
>
> 母本：`..\..\Seed Intelligent Analysis\weekly_report\周报填写要求.md`
>
> 核心原则：**周报负责摘要与导航，WP/靶机笔记负责完整复现与论证。**

## 一、适用原则与优先级

### 1.1 两层文档，不混写

每台靶机至少区分两类文档：

| 文档 | 作用 | 读者 | 内容尺度 |
|---|---|---|---|
| `REPORT.md` / 周报 | 本周进度索引 | 老师、项目负责人 | 短，1–2 页 |
| `WP.md` / 靶机笔记 | 完整技术复盘 | 自己、同学、后续复现者 | 长，允许详细 |

周报不复制 WP 全文，WP 也不套用周报的四大章节。

### 1.2 冲突时的优先级

1. 老师最新明确要求；
2. 本规范；
3. 历史周报或旧模板。

如老师要求与本规范冲突，以老师要求为准，并在下次更新本规范时记录变化。

## 二、周报必须满足的硬约束

### 2.1 固定四段结构

顺序不得调整：

```markdown
# 周报_YYYY-MM-DD

项目名称：……
报告周期：YYYY.MM.DD--YYYY.MM.DD

## 一、遗留问题跟踪

## 二、项目整体进展

## 三、下周计划

## 四、需要老师把关确认的问题汇总
```

不再增设“总体摘要”“技术详解”等并列一级章节。完成结果可作为
“项目整体进展”的第一条结论。

### 2.2 篇幅与信息密度

- 周报目标长度：1–2 页；一般控制在约 2–5 KiB Markdown。
- 一个事项只写一次，详细过程通过链接下钻。
- 周报中最多保留能帮助老师判断进度的小型表格。
- 攻击链、代码分析、配置片段、完整命令和大量截图放入 WP，不直接展开。

### 2.3 遗留问题只写未闭环项

- 已解决事项原则上不再列入周报；需要保留历史时，放入 WP 的时间线或经历记录。
- 无遗留问题时写：

  ```markdown
  - 无遗留问题
  ```

- 仍有问题时使用列表，每条必须给出明确状态：

  - `✅ 已解决`
  - `🔄 有进展`
  - `⚠️ 无进展`
  - `❓ 待老师确认`
  - 不允许只写“处理中”而没有下一步。

- 每条未闭环问题至少写清：当前现象、已尝试方案、下一步动作。

### 2.4 项目整体进展写成“结论 + 链接”

每个主要成果使用父级结论和嵌套链接：

```markdown
- 完成 LAB/phpblog，取得 root 权限并读取 flag。
  - [phpblog 完整解题 WP](仓库内相对路径/WP.md)
  - [phpblog 逐步复现记录](仓库内相对路径/复现指导.md)
  - [关键截图与证据](仓库内相对路径/05_evidence/)
```

要求：

- 父级条目必须让人不点链接也能知道本周成果。
- 子级链接必须指向可打开的仓库内文件或目录。
- 根因和 IoT 映射可在周报中各保留一句结论，但详细论证放入 WP。
- 如果完成结果发生在报告周期之后，必须标明补充完成日期，不能写成周期内完成。

### 2.5 下周计划保持可执行

先写一句总述，再列 2–4 项计划。每项应能判断是否完成，避免“继续学习”“加强理解”这类
无法验收的表述。

```markdown
总述：完成 phpblog 第二遍复现，并转向下一台靶机。

- 按 WP 独立完成一次复现并记录耗时。
- 完成 `<下一台靶机>` 的信息收集与立足点。
- 将模板包含检查点整理为知识卡片。
```

### 2.6 老师确认事项必须可拍板

末尾统一汇总需要老师决定的问题。每条至少包含：

- 已做到什么程度；
- 当前有哪些可选做法；
- 不同选择的影响；
- 希望老师确认的具体问题。

无待确认问题时写“无待确认问题”。

## 三、仓库内链接规则

### 3.1 使用 Markdown 链接，不写裸路径

推荐：

```markdown
- [phpblog 完整解题 WP](../01_targets/2026-W45_LAB-phpblog/WP.md)
```

不推荐：

```text
- 详细过程见 01_targets/2026-W45_LAB-phpblog/WP.md
```

裸路径在 GitLab/GitHub 预览中不可点击，也无法形成快速下钻。

### 3.2 链接文字必须说明内容

推荐：

- `[blogbackup 提权原理]`
- `[低权限 RCE 证据]`
- `[phpblog 第二遍复现记录]`

不推荐：

- `[点这里]`
- `[详情]`
- `[report.md]`

### 3.3 优先使用仓库内相对链接

如周报位于 `02_reports/`，链接到 `01_targets/` 时应写成：

```markdown
[phpblog WP](../01_targets/2026-W45_LAB-phpblog/WP.md)
```

如周报与 WP 位于同一靶机目录，可直接写：

```markdown
[phpblog WP](WP.md)
```

交付前必须实际点击检查链接，不能只凭路径看起来正确。

### 3.4 周报至少链接哪些内容

完成一台靶机时，项目进展下建议链接：

1. 完整 WP；
2. 可执行复现指导或过程笔记；
3. 关键证据目录；
4. 源码审计、漏洞分析或知识卡片；
5. 必要的 flag/root 证明。

无需把每一项都单独列成周报正文。

## 四、WP/靶机笔记规范

### 4.1 WP 不套用周报格式

WP 是技术文章，不是行政周报。推荐结构：

```markdown
# 靶机名：入口漏洞与提权手法

## 靶机信息与结果

## 侦察

## 立足点

## 低权限枚举

## 提权

## 读取 flag

## 根因与防御

## 失败分支与思考

## 与 IoT/科研方向的映射

## 时间线与证据
```

标题应同时包含靶机名和技术主题，例如：

```text
LAB phpblog：模板路径穿越与 root 备份恢复链
```

### 4.2 每一步采用“操作—输出—判断—原因”

关键步骤必须写出：

1. 执行了什么命令或请求；
2. 看到了什么输出或截图；
3. 为什么判断这一步成功；
4. 为什么选择这个方向；
5. 如果失败，下一步如何收窄范围。

只保留决定性命令，不粘贴整屏无关输出。

### 4.3 必须包含真实复现与关键截图

至少覆盖：

- 目标与开放服务；
- 初始入口或异常现象；
- 第一个有效命令执行/文件读取/身份变化；
- 提权所依赖的权限或配置证据；
- root 身份与 flag；
- 清理或回滚结果。

截图要求：

- 同时展示关键命令和关键输出；
- 每张图有编号和说明；
- 图片用来说明结论，不做装饰；
- token、密码、私钥等敏感信息在发布版中打码或删除；
- 截图必须来自本次实际复现，不能只使用他人或 AI 生成的占位图。

### 4.4 保留失败分支和判断变化

WP 不只是成功结果。至少记录一个真实卡点：

```text
我先尝试了 A，但输出 B 不符合预期。
查看 C 后，我判断问题不在 D，而更可能在 E。
改用 F 后得到 G，因此下一步进入 H。
```

失败分支只保留对理解漏洞链有帮助的内容，不要写成逐个尝试的流水账。

## 五、AI 使用与记录真实性

1. AI 可以辅助整理、校对、解释和生成初始框架，但不能替代实际复现。
2. 关键命令、截图、输出和 flag 必须由本人在授权环境中实际取得。
3. 明确标注哪些是：

   - 自己实际执行；
   - 通过离线镜像或源码审计获得；
   - AI/助手提供方向或代为整理；
   - 参考资料或公开 writeup 提示。

4. 不得把“看过 WP”写成“独立完成”，也不得把 AI 推测写成已验证结论。
5. 周报避免“AI 味过重”的空泛总结。优先写具体现象、判断依据和证据。
6. 每台靶机至少保留一次自己的复现尝试记录；如当前仅完成助手复现，应把第二次独立复现
   列入下周计划。

## 六、状态、完成与时间口径

- 状态标签沿用：

| 标签 | 含义 |
|---|---|
| ✅ | 已解决 / 独立完成 |
| 🟡 | 借助提示或资料完成 |
| 🔄 | 有进展 / 进行中 |
| ⚠️ | 无进展 / 未完成 |
| ❓ | 待老师确认 |
| ⏸ | 暂停，须写原因 |

- “拿到 shell”不等于“完成靶机”；必须区分：

  - 信息收集完成；
  - 低权限立足点完成；
  - root 提权完成；
  - flag/证据取得；
  - WP 与复现记录完成；
  - 清理与回滚完成。

- 报告周期按周一至周日。
- 周期结束后补做的结果要标注实际完成日期。
- 未取得 root 或 flag 时，周报必须如实写清卡点，不能用“基本完成”。

## 七、命名与交付

- 周报源文件：`01_targets/<靶机目录>/REPORT.md`
- 导出目录：`02_reports/`
- 导出命名以 `scripts/publish-report.ps1` 实际生成的文件名为准，不手工改名。
- WP：`01_targets/<靶机目录>/WP.md`
- 证据：`01_targets/<靶机目录>/05_evidence/`
- 知识卡片：`03_knowledge/<分类>/<中文概念名>.md`
- 交付前执行 `scripts/publish-report.ps1` 生成副本，确保源文件与交付副本一致。

## 八、交付前质量门禁

每次提交周报前逐项检查：

- [ ] 四大章节齐全且顺序正确；
- [ ] 周报没有复制 WP 全文，主要技术细节已下沉；
- [ ] 项目进展至少有一个可点击的仓库内链接；
- [ ] 链接文字描述清楚，且实际点击可打开；
- [ ] 遗留问题只保留未闭环项，并写清状态和下一步；
- [ ] 下周计划具体、可验收；
- [ ] 老师确认问题可以直接回复；
- [ ] 周期后完成的事项标注真实日期；
- [ ] WP 包含实际复现命令、关键三张以上截图、判断过程和失败记录；
- [ ] 已区分个人操作、离线审计、AI 辅助和资料提示；
- [ ] 敏感信息已打码或移入忽略目录；
- [ ] 清理/回滚状态已核实；
- [ ] 没有 `___`、`{{占位符}}` 或未填写章节；
- [ ] `git diff --check` 无空白错误；
- [ ] `REPORT.md` 与 `02_reports/` 导出副本内容一致。

```markdown

项目名称：打靶机训练（IoT 漏洞挖掘方向）
报告周期：2026.11.09--2026.11.15

## 一、遗留问题跟踪

- 无遗留问题

## 二、项目整体进展

- 完成 LAB/phpblog，取得 root 权限并读取 flag。
  - [phpblog 完整解题 WP](../01_targets/2026-W45_LAB-phpblog/WP.md)

## 三、下周计划

总述：完成第二遍脱稿复现，并开始下一台靶机。

- 按 WP 独立复现一次并记录实际耗时。
- 完成下一台靶机的基础侦察。
- 补充一条模板包含检测规则。

## 四、需要老师把关确认的问题汇总

无待确认问题。
```

## 十、四周自查

每四周检查一次：

1. 周报是否仍然是“进度索引”，而不是 WP 的复制品？
2. WP 是否包含自己的复现步骤、截图和判断，而不是只有 AI 生成的结论？
3. 仓库内链接是否真的能跳转到对应报告和证据？
4. 未完成事项是否如实标注，下周计划是否能形成闭环？
5. 是否至少沉淀了一条可复用的漏洞检查项或研究观察？
